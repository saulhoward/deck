# Internal Rex allocation foundation

**Internal allocation foundation, now used by [public best-effort open/reopen](rex-open.md).** `DeckRuntime.allocateTerminal(...)` creates a Pi-owned administrative task which calls the assigned native Zig worker and commits a full Rex binding. `rex_open`/`openTerminal` adds explicit reuse/new-attempt behavior over this foundation. The public wrapper now resolves an omitted target from local Rex defaults before calling this allocator. No model tool, public Rex draft kind or GUI attachment is shipped. A narrow [allocation-bound client startup observation](rex-startup.md) is now implemented; it is historical evidence, not current health. Use the [installed Rex contract](rex-contract.md) for the tested CLI/version and opt-in isolation rules.

## Identity and authority

The trusted embedding must supply an explicit local target: absolute Rex executable, `unix:///ABSOLUTE_SOCKET` URI, expected Rex `host_id` and `instance_id` UUIDs, absolute Deck client and hub port. The hub/chat identity, saved Deck machine/cwd and deterministic display label are captured centrally. Decoded URI socket paths are bounded to 100 UTF-8 bytes; percent encoding (including macOS `Application%20Support`) is supported. TCP, host aliases, query/fragment and focused targets are not supported. Only the public first-open wrapper resolves local defaults; the allocator always receives and retains an explicit target. External Rex executable contents are not frozen or attested by the implementation fingerprint.

Only managed **ownerless task chats** are admitted. Main, unmanaged and Pi-owned child conversations refuse; misleading `ChatDoc` metadata cannot override Pi ownership. No new conversation, inference, model input or worker-local Pi runtime is created by allocation. Normal central work need not finish before allocation; ordinary configuration still refuses while its administrative task is unfinished. Native I/O does not hold Deck's admission serializer.

Before any CLI call, one Pi commit records:

- the stable per-chat request identity/hash and administrative `deck.rex-allocation` task;
- exact launch inputs, including worker/cwd, server identities, client path, port and hub/chat IDs;
- the chat's sole allocation-attempt task ID and a generated-once allocation UUID in `RexDoc`/task input, used for client startup correlation.

The returned task ID means **admitted, not allocated or ready**. Identical retries retrieve it, including after settlement or later settings changes; changed launch arguments/original expected binding conflict. Missing native capability is refused before admission. The legacy internal entry point remains **one attempt per chat**, even after definite failure, stop or uncertainty. The [public open path](rex-open.md) deliberately allows explicit additional attempts after settlement, accepting duplicate/manual-cleanup risk. It does not reset/replay the original operation; old request IDs still retrieve their original task.

Pi owns scheduling, recovery, stop and results. `RexDoc` is ordinary Pi conversation metadata, not another lifecycle database. `RexRequest` holds identity only. Forks do not inherit these allocation metadata/receipts. Native receipts reuse `worker/operations/<Pi-task-ID>.json`; there is no Rex replay queue or session catalog.

## Native effect boundary

`rex_allocate` is a private native operation, not arbitrary model CLI execution. Its plan and whitelisted creation-result projection now use [schema-derived Zig/TS contracts](protocol-contracts.md): native typed input parsing, serialized egress validation and TS validation before semantic saved-plan comparison. Schema checks do not establish provenance or replace the authority/uncertainty guards below. Settled receipts remain unchanged; legacy absent/null allocation UUIDs and creation-result extensions remain structurally accepted, with extensions omitted from public bindings. The worker checks saved machine/cwd and retains the same request-hash/accepted/result receipt used by native file/bash effects. The requested Deck client must resolve to the worker's own executable, or its public `deck` wrapper when the native entry is `.deck-wrapped`. This preserves private packaged Node/runtime paths without giving the caller arbitrary terminal argv.

All CLI calls use direct argv, explicit `--server`, `--autostart=false`, and Rex's two-second timeout. The shared native owned-process runner enforces a four-second wall limit per call, TERM/KILL cancellation, continuously drained combined 64 KiB output and a maximum of four concurrent process slots **shared with bash**. Raw CLI output must be lossless, untruncated UTF-8 and exit zero. No sampled bash preview is published for allocation. The CLI environment is allowlisted (`PATH`, `HOME`, `USER`, `LOGNAME`, `TMPDIR`, `LANG`, `LC_ALL`, `TERM`, local `XDG_STATE_HOME`, `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, `XDG_RUNTIME_DIR`, `REX_RUNTIME_DIR`), excluding hub credentials, Rex focus/routing, Deck overrides and Node/loader injection. This does not isolate filesystem credentials or sanitize an independently running Rex daemon's environment. The terminal inherits Rex's environment, not the hub's credential environment.

The worker first queries `server status --json`, requiring explicitly supported API revision 8 or 10 and matching endpoint/host/instance. Other revisions refuse before creation; this is not an open-ended minimum-version check. It then issues one creation:

```text
new LABEL --json --cwd SAVED_CWD --shell=none --keep-open -- \
  DECK_CLIENT agent --no-tui --port PORT --task CHAT_ID --hub-id HUB_ID \
    --rex-allocation ALLOCATION_UUID
```

Creation must return one full `session:UUID`, one `window:UUID`, and one `block:UUID`. Explicit `block ls --session FULL_ID --json --short=false` verifies the block's window, local Rex host and shell flavor. A second status query verifies the server identity again. No labels, process display, focused targets, `rex send`, daemon startup or host fallback establish provenance.

Only then does the native worker retain a bounded, whitelisted creation result. An invocation-bound Pi commit rechecks saved chat/worker/cwd and allocation identity, then atomically saves `RexDoc.binding` and terminal task result. The binding contains full server/host/instance/session/window/block IDs, Pi hub/chat/task identity, saved machine/cwd and `readiness:"not_checked"`. Exact launch inputs remain in the Pi task. `terminalBinding()` reads this creation provenance without Rex I/O; it does **not** assert that objects or processes still exist.

## Outcomes, cancellation and recovery

- `allocated`: native creation evidence was retained and atomically bound in Pi. **Not client readiness**, current health or successful inference.
- `not_allocated`: a known pre-create refusal (`invalid`, `offline`, `unavailable`, `cancelled`). No retry/reset UI yet.
- `uncertain`: an accepted native receipt lacks a result; creation/verification failed after issuing `new`; a result is malformed, scoped incorrectly or conflicts; the transport failed; or authority drift prevents applying a possibly earlier effect. CLI stderr/private errors are not copied into Pi outcomes.
- `aborted`: Pi stop settled the invocation without applying a binding. It does **not** mean Rex creation was prevented or undone. Issued CLI work drains/cancels through the native control channel; Rex may already have accepted creation on its independent connection. No automatic session destruction occurs.

Before the first native acceptance, recovery may issue the first creation. An accepted operation without a trustworthy result stays uncertain and is **never reissued**. A retained successful creation repairs a crash before Pi apply without calling Rex again; an already-committed binding/result needs no native call. Stop and raw authority drift cannot fabricate a successful binding. Old attempt identities remain pinned, including uncertainty/abort; repeated old IDs never recreate terminals. Explicit public open may create a new attempt, preserving original receipts/results and the last known binding as history. Missing labels or ambiguous processes never authorize adoption, and reconnect never automatically creates.

Ordinary clients now pin the hub ID learned at startup in subsequent command envelopes; updated hubs reject a mismatched top-level `hubId` before dispatch. The internal `--hub-id` launch option also requires a matching initial identity and advertised `hubGuard:1`, failing closed against an old/incorrect hub before input. This prevents accidental port reuse from redirecting an existing client; it is **not authentication** and cannot distinguish divergent source/restored clones that improperly share an identity. Legacy clients/envelopes remain accepted, and old hubs do not implement this guard.

## Evidence and next boundary

Automated Pi/faux tests cover admission/deduplication/conflicts, ownership/cwd/capability checks, no inference, bounded/private result projection, uncertainty, raw drift and cancellation. Native fixtures exercise explicit argv/server scope, credential exclusion, host/server mismatch, malformed/flooded output, accepted-unsettled receipts, owned-process cancellation alongside independent file I/O, and SIGKILL before native issue, during uncertain creation, after native result retention, after startup observation commit and after Pi apply. Identity tests cover wrong initial hubs/old capabilities and a replaced port preserving the original local draft without sending to the other hub.

The explicit opt-in installed Rex test now also exercises **this production allocation task/native operation** against the private Rex server. It verifies a real full-ID binding/receipt, an early native-block startup registration joined after apply, no canonical input/inference or duplicate session, and historical-not-health semantics after client exit. Evidence covers the observed aarch64-darwin Rex versions/APIs 8 and 10; see the [API 10 revalidation and replacement decision](rex-replacement.md). No live provider, user sessions, GUI or server-restoration evidence is claimed.

[Internal fresh inspection](rex-inspection.md) now reads the saved exact objects on the original worker without mutation, receipts, Pi work or a health cache. It remains separate from the [historical startup observation](rex-startup.md) and retained creation result. [Explicit receipt-based reconciliation](rex-reconciliation.md) can now repair an unbound binding from the exact native retained success, without changing the original task outcome, issuing Rex calls or resetting allocation. Missing/acceptance-only evidence stays unresolved. The [revised local scope](rex-replacement.md) permits public best-effort open/reopen without broader reconciliation, native conditional guards or a new crash-recoverable Rex client draft workflow. [Public open/reopen](rex-open.md) now allows explicit new attempts after failed/unknown creation with a duplicate/manual-cleanup warning, preserving old outcomes rather than replaying accepted native operations. Sampled process presence is not responsive-client readiness. Preserve owned-child inspection/stop-only semantics, and do not automatically retry or adopt the only matching label. Server restart, remote workers/Rex/Tailscale, remote/label-based discovery and GUI attachment remain deferred. Backup preserves Pi intent/bindings/native receipts, **not** Rex objects or external effects; restoring never implicitly creates a terminal, and rollback can forget later effects.
