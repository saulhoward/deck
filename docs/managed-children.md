# Managed children

## Execution and identity

Managed children are Pi **ownerless** conversations with `ChatDoc.kind: "task"` and a separate immutable `managedParentChatId`. They do not use captured `parentChatId`/`ownerTaskId`. Creation validates canonical Pi ownership on the parent and inherits the saved machine/cwd. Managed parents may themselves have children; new immutable older-parent links form an acyclic hierarchy. Captured parents remain forbidden. Captured delegation, naming, invocation-bound submission and foreground cancellation are unchanged.

`create_managed_child` requires a pinned `hubId` and closed arguments `{requestId,parentChatId,title?,problem?,description?}`. Omitting `title` selects problem-only creation: `problem` must be nonblank, well-formed UTF-8 and at most 2048 bytes, and `description` must be exactly `""`. Its canonical title is the permanent name allocated by `wintermute-v1`, in the same transaction; instructions use that exact title. Legacy explicit-title requests retain their original semantics. It returns `{chatId,parentChatId,brief}`. Verified task and launcher attachments may use it only with `parentChatId` equal to their pinned chat. The hub also permits explicit parent selection. Eligible independent clients advertise `managedChildren: 1`, `managedChildOpen: 1`, and `managedChildProblem: 1`; updated clients refuse unsupported creation without falling back to ordinary tasks. Managed-aware native/runtime contracts must be deployed together.

The `deck.managed-child-request` receipt hashes parent/title/brief in its own namespace. Explicit-title hashes remain unchanged; problem-only creation uses a separate hash discriminator and pins the exact problem and empty description, not a guessed title. Creation, agent snapshot, metadata, independent name, grants and receipt commit atomically. Replay returns the original child; changed arguments conflict. No initial input or generation is admitted. Rex opening is a separate best-effort client action after a validated ACK; an uncertain open is never retried automatically.

Parent settings are checked again inside the creation transaction. Snapshotting preserves enabled tools, including nested-call/deferred tools, the offered model-tool subset, registered extensions, model/reasoning and MCP grants. Later parent configuration changes do not track into the child. The child starts with its own brief instructions, not the parent's transcript, loaded-skills history or personal instructions. Availability of inherited tools still depends on the saved host, approved catalog and registration; there is no fallback host or new capability policy.

## Messaging

`parent_message` lives in `deck.task-control`, with its existing causality hook. It infers the parent's ID and admits follow-up input with a stable Pi tool-task request ID, authoritative origin and the shared eight-hop budget. `task_message` remains the parent's explicit route to a child. All agent-origin admissions centrally check independent canonical source/target ownership and direct parent–child adjacency whenever either endpoint is managed. Neither generic `hub_message` nor `task_message` permits sibling, unrelated-agent or non-direct-ancestor messaging. Human input through verified task participation is unaffected. No new execution queue, automatic transcript mirroring or automatic final-answer delivery exists.

An agent may act both as a managed child and as a parent of its own managed children. Communication stays on direct parent–child edges; siblings cannot message each other. Existing foreground captured delegations remain available via inherited tools and their separate invocation/result mechanism.

## Human participation and drafts

The TUI requires **`:new-child PROBLEM`**. It creates a child of the current writable chat; there is no parent-ID argument, template or JSON editor. Bare/whitespace-only commands show usage. The footer accepts up to 2048 UTF-8 problem bytes and refuses submission after overflow until explicit correction/cancellation. The problem's bytes are not trimmed or reformatted, the description is empty, and the server chooses the child's title/name atomically. Prompt text, cursor, editing state and undo history are not creation inputs and survive success, refusal, uncertain ACKs, `:retry`, `:discard`, and explicit `:child-open ID`. Existing forms and unresolved settings/requests still block child creation. Read-only task/captured inspection grants no creation permission.

The saved local draft remains `kind: "task"`, retaining the managed parent, exact problem and `description: ""`, with **no title or host/cwd** in problem-only mode. Absence of title is the durable naming mode; recovery cannot fill in a fresh name. Shared delivery converts `managedParentChatId` to wire `parentChatId`; recovery never substitutes the currently selected chat or current hub binding. Drafts are published privately before sending and removed only after exact parent/brief ACK validation. SIGKILL/lost ACK recovery preserves the same identity and permanent child name. An unrelated unsent prompt is not persisted in this creation draft; detach still warns about losing it.

Legacy explicit-title drafts, the ordinary `:new` form and plain `/new JSON` remain supported. Plain `/retry` can also recover a problem-only draft created in the TUI. No existing draft or title is migrated.

The hub task list and attached-client sidebar label managed parentage without claiming Pi ownership. The top **#CHILDREN** section lists direct managed children separately from **#SUBAGENTS**, with rune/name, sampled status and saved problem (title fallback). It refreshes through ordinary and held/history reads, has no click/navigation or creation effects, and preserves the composer and selected message. Missing data is Unavailable, an empty complete sample is None, stale observations are labeled STALE, and clipped/incomplete samples explicitly show omissions. Discovery reads one bounded descending page of at most 100 canonical conversations and returns at most 16 matching children; older children may be omitted and overflow is not an exact count. Captured inspection never inherits its owner's managed list. Task listing remains bounded canonical pagination, not a full-directory traversal on every poll. `:subagent` / `:parent` and the captured sidebar remain captured-only navigation. Managed agents use ordinary task inspection, Rex, and assigned-worker attachments. A pinned task client cannot navigate into its parent or another managed child, create unrelated agents, or infer general write authority from relationship metadata. Its new creation/opening commands remain pinned to the original parent even while rendering a captured-child inspection. Existing allocation/revocation checks remain in force.

## Same-session terminal opening

`open_managed_child` has closed arguments `{chatId,childId,requestId,port}`: `chatId` is always the authorized **parent**, never a foreign child transport scope. Its ACK is `{parentChatId,childId,ack:RexOpenAck}` with exact parent/child/request correlation. It is a distinct narrow operation; task clients still cannot invoke general `rex_open`, target another parent, supply host/cwd/target/client overrides, or replace the parent allocation.

The runtime checks independent canonical ownership, direct relationship and equal saved machine/cwd. It derives Rex executable/server/host/instance/session from the parent's confirmed allocation, performs native read-only inspection, and rechecks provenance plus outer allocation/revocation guards before serialized admission. The child gets a separate allocation using the current approved worker client/socket. Native allocation uses `rex run --session … --cwd <saved cwd> … deck agent --tui --task <child>`; there is no `rex new` fallback. Parent/child state races refuse. Same-ID replay retrieves the atomic `deck.managed-child-open-request` receipt without another effect; changing parent/child/session/port conflicts. Uncertain prior attempts are not blindly replaced.

New `:new-child PROBLEM` commands freshly read the pinned hub's problem-only capability **before** reserving an identity, so upgrading a connected hub does not require reselecting the chat. New task-client commands/forms also preflight the parent's saved Rex allocation **before** reserving a draft. Missing provenance (including `--here` without a confirmed Rex allocation) refuses creation. Saved creation recovery does not rerun this preflight or retarget the parent. Only exact creation ACK clears the draft; opening is then a separate best-effort action. Losing its ACK never recreates the child or automatically retries the terminal. `:child-open ID` (plain `/child-open ID`) is explicit recovery, stays in the parent view, and uses the same scoped runtime checks.

A creation-preflight failure can carry client-local `TuiResponse.notSent: true`, only before reserving a mutation draft or sending a mutation command. The renderer preserves the unrelated prompt (or a legacy editable form) instead of manufacturing an uncertain request. Remote errors/missing receipts never imply this flag. `:retry` with no unresolved draft is refused locally and cannot lock out explicit child-open recovery.

## Limits and tests

Native tools still run with the OS user's capabilities; coordination checks are not a security sandbox or history-privacy boundary. There is no reparenting, automatic result relay, model-facing managed creation tool, or adoption of arbitrary current-terminal Rex context. Same-session opening requires the parent's confirmed Rex allocation. `deck agent --here` inside Rex can register its exact verified block/client on startup; outside Rex it remains allocation-free. Registration is distinct from child opening and is never available as a general task-client operation. A Rex session can contain many agents, each with its own block/allocation; registration never claims the whole session. Prior allocation attempts and competing block claims refuse rather than replace. After a registered HERE client detaches, inspection distinguishes `client_exited` from a surviving shell; explicit child opening can still use the verified saved session.

Regression coverage includes atomic rollback and replay/restart/SIGKILL, full/restricted tool and MCP inheritance, independent model settings, stop-parent independence, causal messaging and generic-route bypass denial, framed IPC ACK correlation, attached/remote scope checks, native/TS contract parity, saved client recovery, real PTY creation and unsent-form preservation, and unchanged captured ownership/read-only behavior. Same-session regressions cover local/remote parent pins, nested creation, exact session/cwd/client plans, separate child allocation, revoked-parent races, uncertain open recovery, zero initial model input, native bridge contracts and real PTY own-parent creation/form preservation.

Problem-only regressions additionally cover centrally generated title/name equality, instruction-title consistency, unchanged legacy hashes, name allocation rollback, fresh capability changes, UTF-8/Unicode-whitespace validation, parent-scoped local/remote creation, title-absent draft recovery in both clients, unsent-prompt and undo preservation, and bounded command overflow with no partial submission.

HERE regressions cover native local/remote creation and resume in isolated Rex servers, foreground process/PTY and full identity proof, unchanged saved cwd, separate same-session child allocation with preserved parent prompt/selection, forged/partial context, legacy block conflicts, single-send uncertainty fences, and shell survival after client detach.
