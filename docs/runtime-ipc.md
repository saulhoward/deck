# Private runtime IPC v1

Private transport between Zig and its single TS writer. `deck serve --stdio --mock` inherits stdin/stdout as a testable bridge; no TCP listener is opened in stdio mode. `deck serve --mock` instead connects private child pipes to a Zig loopback HTTP bridge (see below). Checkout builds need `npm run build` and Node 24 on PATH, defaulting to `runtime/dist/main.js` relative to the launch directory. The [Nix package](packaging.md) supplies private Node and absolute runtime paths and runs from any cwd. `--runtime /absolute/path` remains a development override for the child entry point.

## State and writer ownership

`deck init [--directory PATH]` creates a version-1 config containing a persistent random machine ID. Repeating init validates but never replaces it. Default state root is macOS Application Support/deck or Linux XDG_STATE_HOME/deck (otherwise ~/.local/state/deck). For now config and state share this private root; separate XDG config and joined roles are deferred. `--directory` selects a dedicated state directory, **not a workspace**. The directory is made private (0700), config and lock files are 0600. Serve requires prior initialization. Config is replaced atomically on first creation; unsupported versions are rejected rather than rewritten.

Zig acquires a nonblocking exclusive `writer.lock` before spawning Node and retains it until the child exits. The lock descriptor is inherited across exec, and Node keeps it open until process exit. Killing the supervisor therefore does not release the writer lock while its child remains alive. Stale lock files are harmless: the OS releases locks, not filenames. Never delete a lock file to force a second writer. This implementation targets macOS/Linux only.

With `--mock`, the runtime registers no real providers and every model result clearly says it is mock output. Default `serve` now registers OpenAI with ChatGPT OAuth; explicit `--api-key` enables paid-key mode. See [providers and login](providers.md) for setup and unverified live-provider behavior. All modes now include a Zig native-file worker on dedicated inherited pipes; see [local tools](local-tools.md) for capability and uncertainty limits. [Bash](shell-tools.md) uses a third, dedicated inherited cancellation pipe and bounded execution threads. No startup downloads occur. The launcher also passes its actual native executable path for implementation fingerprinting. [Startup compatibility](recovery-compatibility.md) checks canonical work before Harness normalization/resume; rebuild Zig and TypeScript together after this private child-argument change.

## Framing and envelopes

Each frame is a four-byte unsigned big-endian byte length followed by UTF-8 JSON. Frame bodies must be objects and are limited to 1 MiB in either direction. Zero-length, invalid UTF-8/JSON, truncated frames and incompatible envelopes terminate the connection. Stdout is protocol-only; diagnostics go to stderr.

Request:

```json
{"version":1,"id":"transport-request-1","command":"status","args":{}}
```

Success:

```json
{"version":1,"id":"transport-request-1","ok":true,"result":{"mainChatId":"1","activity":{},"tools":"native-files + bash"}}
```

Failure:

```json
{"version":1,"id":"transport-request-1","ok":false,"error":{"code":"invalid","message":"Unknown command"}}
```

Requests may also include top-level `hubId` (nonempty, at most 200 characters). Updated hubs advertise `status.hubGuard:1` and reject mismatches with `conflict` **before dispatch**, including reads, admissions and stop. The client pins its initial hub ID on subsequent requests so port reuse does not silently redirect work. Internal Rex `--hub-id` clients require the matching initial identity and guard capability before input; legacy envelopes remain accepted, and old hubs lack this protection. This is identity-drift prevention, not authentication or divergent-clone detection.

The [schema-derived request-envelope guard](protocol-contracts.md) is shared by Zig HTTP and private TS IPC. It validates version, ID and string command; v1 envelope extensions remain allowed, while command args and expected-hub checks still run separately. Missing/non-string private commands now fail envelope validation, matching the public boundary. Response envelopes and bounded error records now also use generated contracts. Closed success/error `oneOf` variants require boolean `ok`, version, ID and exactly `result` or `error`. Unknown well-shaped lower-case error codes remain allowed; messages are nonempty and at most 4,096 Unicode code points. Arguments and ACKs for `admit`, `create_task`, `import_instructions`, `stop` and `rex_startup` are also schema-migrated; `list_chats` now has generated arguments and bounded item/page contracts too. `history` now also has generated arguments and bounded entry/page/rendered-payload views, plus request-scoped ordering/cursor checks; its attached activity/progress/instruction views and their standalone read commands also use generated closed snapshots/arguments with safe-ID, explicit chat/task scope, UTF-16 and state/result consistency checks. See [live-view contracts](live-view-contracts.md). Public `rex_open`/`rex_status`/`rex_inspect` now also have generated command contracts and scope/identity checks; see [Rex open/reopen](rex-open.md). Startup `status` and all four `login_*` commands also use generated contracts with identity/state checks; see [status/login contracts](status-login-contracts.md). Command-specific failure guidance and private native request/result/progress/receipt views are now schema-backed too; see [client foundations](client-foundations.md). This does not define a remote protocol or full Pi archive schema.

IPC validates serialized response egress: missing/invalid fields or serializer failures become a generic correlated `invalid_response`, not a success or proof nothing executed. Zig HTTP validates private reply UTF-8/envelope and exact transport-ID equality before forwarding original bytes; an invalid/mis-correlated private response closes that client connection and stops the out-of-sync transport with no replay. The plain client independently validates shape and exact ID before exposing results/errors, then checks command-specific ACKs/views. Responses lacking version/ID, using truthy nonboolean `ok` or mixing result/error now refuse, preserving saved mutation drafts for explicit recovery. The three saved mutations additionally require generated command-specific args/ACKs. Args are checked client-side and before private dispatch; serialized ACK egress, native HTTP forwarding and the client validate ACK shape, safe positive string IDs and exact import chat/request echoes. All three ACKs reject extra fields. Admission/create args retain legacy ignored extensions; import args remain closed. Existing UTF-16 bounds and runtime authority checks remain separate from schema lengths. Legacy drafts failing new wire checks stay unchanged with no send or automatic migration. Stop additionally uses generated arguments (legacy ignored extensions allowed) and a closed `{requested:true}` ACK, with no durable draft, drain/completion guarantee or automatic retry. Startup arguments/ACK are closed, require full IDs and explicit expected hub plus exact echoed chat/allocation/block identities, and accept only historical `unbound|matched` registration with `live:"not_checked"`. These administrative ACKs run through the same private egress/native forwarding/client validation, without widening ownership or creating another retry queue. Neither an error nor a disconnected transport proves a mutation did not commit. No payload contents/private serializer diagnostics are logged.

`id` is a nonempty transport correlation string (at most 200 Unicode code points, not bytes or UTF-16 units), not a durable request identity. At most 16 commands are active; additional commands receive `busy`. Output writes respect stream backpressure and remain within that active-command bound. Responses may be out of request order. Oversized results return `too_large`; history supports smaller pages, though a single oversized entry still cannot fit this transport. EOF closes the runtime/store; it does not invoke conversation abort. Stopping the runtime leaves interrupted Pi work recoverable on reopening under the same implementation; a changed build refuses unfinished work rather than silently adopting it.

`list_chats` scans Pi's canonical conversation records and reads existing Deck metadata, including main, tasks assigned to offline hosts and foreground subagents. Child rows include optional `parentChatId`/`ownerTaskId` display links; Pi's ownership edge is authoritative. It creates no documents, conversations or inference. `next` is the last **scanned** ID; pass it as `after` for the next page. Pages can be empty while still returning `next` if scanned Pi conversations have no Deck metadata. The limit bounds scanned records, not matching items or encoded bytes; the existing frame-size error still applies. Generated args/items/page guards run before private dispatch, on serialized egress, before native forwarding and at client consumption. Page/item fields are closed; request extensions remain ignored. Safe string IDs, ascending exclusive-after order, count within the requested limit, paired safe display links and a next cursor strictly after the request/not behind the last visible item are semantic checks. Optional cursors/links may be absent, not null. Labels are well-formed strings up to 200,000 code points (including empty display metadata, not host/cwd authority); invalid stored metadata fails the read without clipping/repair. The client validates the entire page before displaying rows or changing its cursor; invalid/lost pages require explicit `/tasks more` at the prior position, not mutation `/retry` or automatic discovery replay. Existing drafts remain unchanged. Pages are not a frozen snapshot: newly created higher IDs may appear on subsequent pages. This is client discovery, not an activity/lifecycle catalog or a public Rex allocation API. The [Rex allocation foundation](rex-allocation.md) now backs the explicit public `rex_open` command; `rex_startup` only records an already-admitted allocation's client observation. [Fresh Rex inspection](rex-inspection.md) is also exposed through `rex_inspect`, independently of the historical `rex_status` view. These are operator commands, not model tools. Those ephemeral cancellable reads create no native receipts or Pi work; the historical startup projection is unchanged. [Explicit creation-provenance reconciliation](rex-reconciliation.md) is a separate internal Pi administrative task: its native receipt lookup dispatches no effects, stores no lookup receipt and exposes no new hub command. Model-facing inspection/control and foreground delegation are documented separately.

`history` delegates to Pi's fork-aware canonical entry scan, including retained history before resets/compaction. Both `before` and `after` bounds are exclusive; specifying both is invalid. Keep `chatId` unchanged and pass the returned `next` as `before` to walk backward, or as `after` to walk forward. Omit both to read the newest page. `after:"0"` means from the beginning, which also lets an empty-chat client begin incremental observation without racing the first append. Positive bounds are safe integer entry-ID strings. Entry IDs need not be consecutive, and parent entries inherited by forks obey Pi's fork boundary. New appends do not move an existing backward cursor. No transcript mirror or server-side browsing session is created. `next` is now a Deck entry-ID string rather than the previously exposed incidental Pi cursor object; prototype clients consuming that field need updating. Items retain Pi's numeric entry IDs and existing entry representation. [History boundary validation](history-contracts.md) checks the whole page and rendered payloads before output or cursor advancement at private egress, native forwarding and client ingress. Numeric entry IDs are never coerced from strings/booleans; pages obey the requested limit/exclusive scan order, and `next` must equal the final row's ID (empty pages cannot advance). Unknown Pi entry kinds/record extensions remain intact and unrendered, not silently dropped from cursor accounting. A smaller `limit` can repair a `too_large` response without advancing the requested cursor, unless a single entry itself exceeds 1 MiB.

Conversation/submission IDs are strings at this boundary even though Pi 1.4.0 uses internal numeric IDs. Admission ACKs acknowledge durable Pi submission only, not generation completion. Retry `admit` using the same durable `requestId`; mismatched text/mode returns `conflict`. `create_task` also requires a durable request ID: its task/conversation and receipt commit together in Pi, and conflicting retries reject. `stop` uses Pi abort semantics, including withdrawing queued input and aborting/draining ordinary owned foreground children; it does not stop other ownerless task chats. Foreground subagent chats can be inspected/stopped but external `admit` is rejected: input comes only through the owning tool's Pi handle. See [subagent ownership and input limits](subagents.md). There is no additional request-cancellation protocol yet. General settings remain unexposed while full per-input pinning is incomplete. The narrow exception is an explicitly idle-only [instruction import](instruction-import.md): the client freezes its target binding before send, the hub blocks ordinary new input during the Pi task, and application/source/result commit atomically after a retained worker read. Instruction status reads are read-only, bounded and scoped to import task kind/chat; task admission is not application. No model tool, automatic loader or arbitrary path is exposed. New capture metadata is explicitly an admission-time observation, not a frozen agent bundle. Repairing an unadmitted reservation after observed settings drift returns `settings_changed` without submitting; already admitted receipts remain retrievable. Internal configuration checks Pi's authoritative tasks/inbox atomically, including draining effects. See [settings semantics](settings.md).

## Loopback HTTP and plain client

The shared plain-client transport validates actual serialized requests and bounds HTTP response bytes to 1 MiB before parsing, independently of Content-Length. Invalid UTF-8, truncation, oversized bodies and redirects refuse without mutation retry. The ten-second deadline and detach signal remain. Shared Zig/TS failure policies distinguish repeatable reads (including same-cursor history page reduction), explicit unchanged saved-request retry, terminal inspection and transient login observation. Neither a remote error code nor HTTP failure proves a mutation did not execute. See [the policy table and Zig client entry points](client-foundations.md).

```sh
# From the repository, after building Zig and TypeScript (mock demo state):
./zig-out/bin/deck init --directory /tmp/deck-demo
./zig-out/bin/deck serve --mock --directory /tmp/deck-demo
# In another terminal:
./zig-out/bin/deck agent --no-tui
./zig-out/bin/deck agent --no-tui --message 'Hello'  # ACK and detach, not wait for an answer
./zig-out/bin/deck agent --no-tui --task 2           # select an existing conversation
```

HTTP mode binds **only** `127.0.0.1:52800`; `--port N` overrides the port on both serve and agent. `POST /v1/command` accepts the same v1 JSON command envelope and returns a JSON response envelope. Application errors use `ok:false`; HTTP syntax/security errors use 4xx. All requests must have the exact `Host: 127.0.0.1:PORT`. All Origin-bearing requests are rejected. No CORS, browser support, remote bind or authentication claim is made. As in the architecture, loopback trusts local OS users. Request heads are bounded to 8 KiB, bodies to 1 MiB, with three-second socket read/write timeouts.

This intentionally small bridge handles HTTP/IPC roundtrips serially, but inference continues independently in TS and admission never waits for generation. Native file work uses separate pipes and a Zig thread, not this roundtrip loop. Stop returns promptly as a non-durable stop-request receipt; Pi continues scoped abort/draining while other commands can proceed. It does not claim effects have stopped or been undone. Live SSE is not yet implemented. Writer failures are now monitored without requiring a client request (below).

Plain mode uses line input, loads an initial tail of up to 100 canonical entries, then fetches forward from its last observed entry ID. Only cursor/summary state is retained, not a growing set of displayed IDs. It emits no ANSI and strips terminal control sequences from displayed content. It is not a raw-mode editor or complete scrolling history implementation. `/status`, `/activity`, `/stop`, `/older`, `/tasks`, `/tasks more`, `/select CHAT_ID`, `/main`, `/task TITLE`, `/instructions [load|TASK_ID]`, `/rex [open|reopen|status|inspect]`, `/retry`, `/discard`, `/help`, `/exit` are supported. `/tasks` lists the first 25 scanned records (including main); `/tasks more` advances without changing the selected chat. `/select` validates an existing chat before switching; `/main` returns to main. Selection clears the displayed page and fetches the selected history; stale in-flight history from prior selections is ignored. Switching only changes this client's selection, never creates work or aborts the previous chat. `/task` creates/selects an independent task conversation on the selected chat's host/cwd. Interactive and one-shot unacknowledged admissions/task-creation requests, and interactive instruction imports, save their IDs and original chat/binding arguments privately before sending. See [durable client drafts](client-drafts.md) for recovery, storage and multi-client limits. `/draft`, `/drafts`, `/recover REQUEST_ID` and `/discard [REQUEST_ID]` inspect/manage this cache; recovery never automatically resends. Switching or creating another task is blocked until `/retry` succeeds or `/discard` explicitly forgets the draft. Discard is local: it does not undo or cancel work that may already have been admitted despite a lost ACK. On reconnect/selection, a saved request for that original chat becomes active for explicit `/retry`; other saved requests remain available through `/drafts`. Ctrl+C and exit detach without aborting Pi work; pending client HTTP reads are cancelled and late responses are ignored. Detaching with an unresolved draft prints a warning: it may already be admitted, and recovery requires the local save to have succeeded. A save failure prevents sending, but leaves new input memory-only. One-shot `--message` prints the durable submission receipt; it does not wait for inference. Agent-sent task inputs carry Pi-origin metadata and display as `agent chat ID`, not `you`; model task control is documented [separately](task-control.md). The HTTP admission command does not accept caller-supplied origin metadata.

### Older history in plain mode

`/older` walks backward from the oldest entry in the first recent page loaded for this selection. Each page is printed as a labeled older-history block, oldest first within the block; the terminal is not redrawn or prepended. A failed fetch leaves the cursor unchanged: retry `/older`, not `/retry`. Once exhausted, it reports no older history. Selection resets the browsing cursor. User/assistant text is rendered with the same control stripping as recent output; tool-call names and settled tool results are also rendered. System entries remain paginated but not rendered.

Recent polling and backward browsing keep independent cursors and page-size limits. Polling never resets the browsing cursor, and older IDs never advance the forward watermark. Both automatically halve their page limit on `too_large`, down to one entry, and retain the successful smaller limit for this selection; other errors leave cursors unchanged. Later automatic forward polls retry the same position; `/older` requires an explicit retry. A single oversized entry remains an explicit error. No unbounded display cache or automatic full-history download is added.

### Forward catch-up and detach

Within the current selection, each poll reads at most one ascending page after the last successfully displayed/observed ID. The watermark advances only after a validated page is rendered; all entries, including unrendered system entries, count. Empty pages leave it unchanged. Bursts larger than a page and transient hub/transport failures therefore do not jump over committed entries: subsequent polls resume the same position and drain the backlog in order. One page per poll bounds each catch-up step and leaves commands responsive; a sustained arrival rate above the drain rate can still grow the backlog. Activity is sampled at current time, independently of how far the displayed transcript has caught up.

This requires the updated hub and client together; restart `serve` after updating the runtime. It assumes the same store remains available and retains its history. A single oversized entry blocks progress with an error rather than silently skipping it. Selection/client restart deliberately starts a fresh bounded tail; the observation cursor is not persisted across client crashes, and older retained entries remain accessible via `/older`. Every supplied live attachment must validate before any part of its page renders or the cursor advances. Malformed/wrong-scope attachments fail the read without changing preview/instruction deduplication or saved mutation drafts; missing optional samples are not clearing claims. These are committed-entry catch-up guarantees, not durable terminal delivery or preservation of provider partials/unretained shell bytes. [Sampled provisional previews](live-progress.md) and sampled native-bash tails are separate from this cursor; SSE, lossless streaming and arbitrary tool partials remain unfinished.

Detaching aborts only this client's HTTP transport, not a Pi submission, tool or conversation. It does not send `stop`. Ctrl+C can therefore detach promptly while a catch-up read is stalled; ordinary connection closure still never means aborting hub-owned work.

### Activity and tool results

The plain client requests `history` with `includeActivity:true` on recent polls, and prints an `activity:` JSON status line only when the bounded summary changes. The first idle snapshot is quiet. `/activity` explicitly prints the selected chat's current summary; `/status` retains the broader global Pi inspection for diagnostics. Selection resets observation cursors and activity deduplication and ignores stale responses. Older-history fetches do not change the live display state.

`activity` contains `chatId`, Pi's `busy` run flag, queued submission count, optional `runTaskId` and generation `{attempt,phase}` (`generating`, `retrying`, `deferred`), up to 32 primary/nested tool summaries (`callId`, `name`, `status`, optional `taskId`, `nested`), `omittedTools`, compaction count and a compaction-failure flag. Call/name strings are bounded to 128/80 code units. Arguments, inbox content, provider errors, partial model text, tool output and arbitrary details are deliberately omitted. The underlying live/inbox/history reads sample committed state separately, not one atomic revision. This is a current presentation, not an event log, execution authority, admission ACK, proof of worker availability, or guarantee of OS process cleanup. Short transitions between polls can be missed. Nothing is stored outside Pi except the client's display fingerprint.

Retained assistant tool calls print names, not arguments. Canonical `pi.tool-result` entries print an ok/error flag, selected native metadata (code/exit status/truncation), and at most an 8K-character text tail after control stripping. Display clipping is labeled and does not alter the canonical result; non-text content gets a placeholder. An error/uncertain result does not mean the effect did not happen. Refreshing/rendering never reissues a tool.

Provider text and running native bash now have separate [bounded provisional snapshots](live-progress.md), requested with `includeProgress:true` on recent polls or standalone `progress`. They are not attached to older-history browsing and do not change the history cursor. Optional previews/instruction samples are omitted if their combined attachment would overflow an otherwise fitting history frame. Recent polling also requests `includeInstructions:true`, rendering bounded changed snapshots of current source provenance and the latest Pi import task. `/instructions [TASK_ID]` explicitly reads those facts without reloading; `/instructions load` is the separate saved-before-send mutation. Source and task are sampled separately, and a historical `applied` receipt is not proof that its text is still current. See [instruction status and limits](instruction-import.md). Bash snapshots are sampled replacement tails, not append deltas or effect receipts; arbitrary tool partials, lossless shell streaming and SSE remain unfinished. Activity snapshots are not an event log or a replacement for the canonical transcript and forward entry catch-up.

## Writer failure and shutdown

In HTTP mode, Zig checks the writer's process status every 100 ms while idle in the listener loop and while waiting for IPC response bytes. It reaps only that exact child and caches its termination status for the normal `Child.wait` cleanup; native shell children retain their own waiters. Unexpected writer death, including exit code zero, stops the listener and exits serve nonzero with a generic `runtime unavailable` diagnostic. There is no automatic respawn, effect retry or second store owner.

The runtime also observes Pi's public `harness.closed` result. A failed Harness/store triggers a generic diagnostic and writer shutdown without logging the failure payload. Ordinary model/tool failures are not fatal store failures. Native request/control/result pipes are closed and their asynchronous close events awaited before forcing Node exit: an outstanding fs.read on the inherited result pipe can otherwise leave Node's libuv thread-pool shutdown blocked. Pi remains the canonical owner of pending work; the Zig worker drains file work and cancels owned shell groups when its channels close, retaining receipts where possible.

These are death/failure checks, not a heartbeat or live-hang watchdog. A living writer stuck in computation or effect draining is not automatically killed. HTTP header/body handling still uses three-second per-I/O socket timeouts and can delay process checks; those are not a total request deadline. A hard supervisor kill and deliberately escaped shell sessions retain the cleanup limits described in [shell tools](shell-tools.md).

After a failure, inspect pending work and uncertain effects before restarting the same serve command/state/mode. Never delete the writer lock. Existing clients retain their in-memory observation position through transient reconnects, and saved unacknowledged drafts can be explicitly retried after client exits. Transcript observation cursors are not durable.

## Validation

```sh
nix develop -c zig build
nix develop -c zig build test
DECK_TEST_BINARY="$PWD/zig-out/bin/deck" nix develop -c npm test
```

The supervisor test initializes a fresh directory, checks permissions/idempotency, sends framed requests, checks durable dedup/conflict, kills Zig while Node retains the writer lock, then drains/closes the child and reopens the same main chat. It uses no credentials. Response fault tests inject wrong IDs, missing result, nonboolean success, mixed payloads, wrong versions, malformed JSON and invalid UTF-8 from the private writer. They verify no invalid ACK is forwarded, no dispatch replay occurs, and the listener closes/releases its port. Further cases reject unsafe/extra-field command ACKs, mismatched import chat/request echoes, invalid stop receipts and wrong startup identity/health claims. Administrative tests prove stop ACK does not wait for held draining, no stop draft/automatic retry appears, an existing input draft stays intact, and malformed startup ACKs never unblock interactive input. Discovery tests additionally reject malformed/unsafe/extra metadata and invalid ordering/last-scanned cursors, forward valid sparse/terminal pages, and preserve the cursor and existing drafts across malformed/lost pages without partial rendering, automatic pagination or inference. Client tests retain input/task/import drafts across invalid envelopes and ACKs, preserve newly refused legacy draft bytes without sending, and require explicit same-argument retry with the original durable identity. Additional fault tests kill an idle writer, request an unexpected clean exit, kill during IPC, and kill while a TERM-resistant native shell runs. They verify nonzero hub exit, port release, shell cancellation/retained receipt and store reopening. A separate synthetic Harness-failure notification exercises the real runtime shutdown path and checks that private error text is not logged; it is not a claim of complete SQLite fault-injection coverage. Without DECK_TEST_BINARY the runtime-only tests run and supervisor/fault integration tests are explicitly skipped.
