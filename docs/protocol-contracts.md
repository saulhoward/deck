# Schema-first wire contracts (initial subset)

**Implemented foundation, not complete protocol migration.** `contracts/wire.schema.json` is the single authored source for request and success/error response transport envelopes, bounded command-error records, the existing native Rex allocation plan/creation projection, [internal fresh inspection](rex-inspection.md) scope/query/observation/timed snapshot and [creation-receipt reconciliation](rex-reconciliation.md) lookup/evidence projection. It does not yet define command-specific hub args/results/error semantics, all native effects, the other client snapshots or remote workers. Those boundaries retain their existing handwritten checks. There is no new inspection/allocation hub command, replay policy or readiness claim.

## Source and generation

The schema declares Draft 2020-12 and uses a deliberately small supported subset. `scripts/generate-contracts.mjs` produces:

- `src/generated/contracts.zig`: typed native views, structural validators over `std.json.Value` and validating typed JSON parsers;
- `runtime/src/generated/contracts.ts`: TypeScript wire types and executable type guards, with no runtime schema loading.

Do not edit generated files or duplicate these wire shapes in another language. Internal domain types may adapt them—for example, new Pi allocation intents never generate a null UUID, while legacy native records may contain null. External Rex API responses still have their own bounded validating adapter; Deck's schema does not purport to define Rex's API.

Use the pinned development shell (Node 24 and Zig 0.15.2):

```sh
nix develop -c npm run contracts:generate
nix develop -c npm run contracts:check
```

Generation formats Zig with the pinned compiler. `--check` compares both generated files without writing them. `npm run check` and the Nix build run this gate, so stale artifacts fail CI/package builds. Generation is local and deterministic; it fetches no remote schemas or tools and adds no npm dependencies. Installed runtime validation is inlined in compiled JS/native code and covered by the implementation fingerprint; neither schemas nor the generator are needed at runtime.

## Supported subset and limits

The compiler accepts local `$defs`/`$ref` without recursive references, object properties with explicit required/additional-property policy, unconstrained JSON values, strings with code-point length limits and restricted patterns, bounded safe integers, booleans/null, scalar constants, closed identifier-string enums, nullable `anyOf` pairs and bounded discriminated object `oneOf` variants. Unsupported keywords and shapes **fail generation**, rather than being ignored by one validator. Enum members are distinct ASCII lower-case identifiers (`[a-z][a-z0-9_]*`), generating Zig enums, TS literal unions and exact executable guards. Mixed/numeric/arbitrary-string enums fail generation. A `oneOf` requires 2–8 object branches with a common required property whose scalar constants are distinct, proving branches disjoint before generating OR guards. TS gets a union; Zig gets a tagged union with validating JSON decoding and unwrapped payload encoding (no `case0`/`case1` wire tags). Reserved Zig field names such as `error` are escaped by generation. Arrays, nondiscriminated/general unions, formats, recursive schemas and arbitrary regexes require a deliberate compiler extension and parity tests before use. This is not a general-purpose JSON Schema engine.

Patterns use anchored ASCII concatenations, positive character classes/ranges and bounded repetitions; variable repetition must be final. The strict end marker `$(?![\s\S])` avoids JavaScript `$` accepting a match before a trailing line terminator. Zig compiles the same restricted pattern to non-backtracking token checks. Do not replace the strict marker with `$` alone.

JSON Schema string lengths count Unicode code points, not UTF-8 bytes or UTF-16 code units. String guards additionally require well-formed Unicode; Zig's JSON parser rejects lone surrogate escapes, and TS rejects corresponding ill-formed strings. The request transport ID is now uniformly 1–200 code points, replacing Zig's byte-based and TS's UTF-16-based checks. ASCII UUID clients are unchanged. Existing path/socket/output **byte** limits remain explicit native semantic/transport checks.

Numbers are bounded within JavaScript's safe-integer range. Integral JSON numeric spellings such as `1.0`/`1e0` are accepted as integer 1; strings, fractional/out-of-range values and non-finite JS-only values are not coerced into valid integers. Opaque wire IDs remain strings. There is no canonical JSON hashing/re-encoding change.

Callers must bound encoded input before parsing: HTTP/IPC retain the 1 MiB frame/body limit, native allocation/inspection projections retain 16 KiB bounds, receipt lookup allows 128 KiB embedded request bytes/256 KiB encoded query with a 16 KiB reply, and CLI output/timeouts/capacity remain separately bounded. Schemas do not establish parser resource safety, authentication, ownership, host affinity or effect replay safety. Parsers retain their existing duplicate-member behavior; this foundation does not promise identical JSON parsing for every malformed/ambiguous input.

## Current application points

- **HTTP and private IPC:** both validate `RequestEnvelope` before dispatch. Unknown v1 envelope extensions and unknown command strings remain accepted structurally; dispatch still refuses unknown commands. `args` and `hubId` deliberately remain unconstrained at this transport layer. Command validation and hub pinning still run separately, with mismatch checked before command dispatch. Missing/non-string command fields now fail private envelope validation, matching the existing public boundary.
- **Response egress, HTTP forwarding and client ingress:** private IPC validates the actual serialized `ResponseEnvelope`, not just the in-memory TS type. Closed success/error variants require a literal boolean `ok`, version, transport ID and exactly the corresponding payload. Errors require a lower-case identifier code (1–80 code points) and a nonempty well-formed message (at most 4,096 code points); unknown well-shaped codes remain allowed. Opaque success `result` is deliberately unconstrained here, not a command-specific ACK. Serialization/shape failure yields a payload-free correlated `invalid_response`; frame overflow remains `too_large`. Dispatch may already have committed, so neither error proves no effect. Zig validates private response UTF-8/envelope and exact request-ID equality before forwarding original bytes; invalid/mis-correlated responses close that HTTP connection and stop the out-of-sync transport, without retry. The plain client independently checks the generated envelope and exact ID before exposing results/errors, then runs existing command-specific ACK/view checks. Invalid responses cannot clear input/task/import drafts; only explicit same-durable-ID retry is allowed. This is correlation, not authentication, selection-generation fencing or a complete command migration. Old fake/legacy responses without version/ID or with envelope extensions now refuse.
- **Native Rex allocation input:** Zig validates/parses the generated `RexAllocationPlan`. Unknown plan fields refuse. Original worker/cwd, absolute paths, explicit socket/host/instance, executable identity, environment, timeout and cancellation checks remain semantic requirements before creation.
- **Native creation output:** Zig constructs the generated creation type and validates the serialized projection before retaining success. A malformed post-create projection remains uncertain, never a known pre-create refusal. TS validates `RexCreation` before comparing it to the saved plan and atomically applying the binding. Schema validity never substitutes for allocation/hub/chat/worker identity.
- **Fresh inspection:** generated exact scope/query and closed presence/status records validate native ingress/serialized egress and TS ingress/final timed projection. Unknown inspection fields/variants refuse, private fields are not projected, and original worker/binding/request-generation and exit-code/state consistency are separate semantic checks. Read failures become inconclusive, never missing. No read receipt, Pi task or public command is added.
- **Native creation-receipt lookup:** generated query/receipt/state/hash types and validators serve a separate read-only boundary, not effect dispatch. Native checks the original operation/machine/cwd and exact byte hash; TS checks that same hash and original-plan identities before provenance apply. Missing/acceptance-only evidence cannot become allocation permission. State/creation consistency remains a semantic guard.
- **Legacy records:** absent/null allocation UUIDs remain structurally accepted. Creation-result extensions remain accepted for compatibility, but are never copied into the whitelisted public binding. Settled Pi results/retained receipts are not migrated or rewritten. New plans still bind their generated UUID semantically; startup registration remains historical, not adoption authority.

Generated Zig typed parsers are **views**, not lossless archive codecs: they can omit accepted unknown extensions and normalize absent optional values to null when serialized. Guards enforce required/unknown-field policy at every nested object before typed decode. Typed decoding then ignores already-validated extensions so a strict parent can correctly contain an extensible legacy creation record; strict nested objects still reject unknowns. Forward the original validated HTTP bytes and preserve original retained receipts; do not round-trip them through typed views for storage/hashing/replay. Encoding a struct alone is not validation; validate serialized egress where the contract requires it.

## Validation and next boundary

`src/contracts.test.json` is the shared 115-case positive/negative corpus used by native Zig and TS tests. It covers missing/null/optional values, required/unknown fields, versions, ID formats, bounds, astral Unicode, trailing newlines, unsafe/fractional numbers, legacy projections, response discriminants/error bounds, inspection enums/scopes, explicit absent observations and bounded exit/revision fields. Zig tests also decode and re-encode typed views and require the resulting projection to remain valid. These are shape round trips, not byte/extension-preserving serialization claims.

Generator tests exercise determinism and refusal of unsupported keywords, references, patterns, numeric bounds, enum members and overlapping/missing-discriminator/recursive/oversized unions. HTTP integration tests prove malformed envelopes are rejected without killing the writer, Unicode limits agree across both guards, and semantic argument checks remain active. Existing Pi/native Rex tests cover scope, private-field omission, retained results, stop, uncertainty and crash windows using the generated boundary.

Response tests additionally inject malformed/mis-correlated replies after a simulated committed mutation, exercise both union codecs (including nested native decoding), verify no private serialization/error diagnostics escape, and require all three draft kinds to survive invalid envelopes before explicit exact-argument retry. Native HTTP faults verify the connection/listener close without forwarding or replay. Validation for the current response slice on aarch64-darwin: Zig formatting/tests/build, TS checks, the full 219-test suite (217 passed, two opt-in tests skipped), `nix flake check path:.` and package build all passed. Separately, installed package smoke passed 1/1 and the isolated Rex API 8 contract passed 10/10. The synthetic Harness-failure test now waits for its observer to be installed before measuring the existing shutdown deadline; listener readiness alone precedes runtime fingerprinting/open. No live provider, live hub refresh, user Rex sessions, remote worker, GUI/server restoration or other-platform validation is claimed.

Next: broader reconciliation and explicit replacement can build on fresh inspection and exact retained-creation proof repair, while remaining command-specific ACKs/args/results/error semantics, effects and views continue migrating to the generated path. Complete that migration before remote workers or another client implementation. Keep creation provenance, historical startup and fresh observations separate; do not build a second health/lifecycle store.
